## Final whole-branch review (opus)

Verdict: Ready to merge — With fixes. 0 Critical, 1 Important, 9 Minor.

Important: (1) `toBrandingDto`'s `logoUrl` is a constant string (`/api/admin/branding/logo`) regardless of which logo file it points to — replacing an existing logo produces byte-identical response JSON before and after, so React never re-requests the `<img>` (same `src` = no DOM attribute change = browser keeps showing the decoded old image) until a full page reload. Reviewer traced exactly why every prior check missed this: the backend tests assert the string/bytes (correct, but never touch an `<img>` element), and Task 5's live verification walked exactly one linear path (unconfigured → set all three → verify → clear all → verify) that never replaced one logo with a different one — the only scenario that exposes the bug.

Minor (9, see full review text for all): (2) the settings page always sends `primaryColor` on save (initialized to Bootstrap's default hex), so an Admin who only wants to change the logo also silently writes an explicit color override, and that default's runtime-computed hover shade visibly differs from Bootstrap's own SASS-derived hover shade; (3) no re-validation of the stored `primaryColor` hex on the read path before CSS interpolation — low severity (assigning to `textContent` can't break out of the style tag) but a real defense-in-depth gap on an unauthenticated route reachable by any future out-of-band writer; (4) button text color (`--bs-btn-color` etc., hardcoded white by Bootstrap) isn't adjusted for the accent color's luminance — a light accent color makes primary buttons genuinely unreadable app-wide including the login page; (5) unsaved form edits are silently reverted by any background refetch (React Query's default `refetchOnWindowFocus`/`staleTime:0` plus a `useEffect` keyed on the `config` object identity); (6) the logo upload inherits the full attachments MIME/extension allowlist (PDF, CSV, TXT, DOCX) rather than an image-only one — Admin-gated, low severity; (7) the old-logo cleanup unlinks before the DB upsert commits, so a crash/throw in between leaves the DB pointing at an already-deleted file (reviewer confirmed swapping the order makes the failure mode a harmless orphan instead of a broken reference); (8) no client-side `maxLength=100` on the app-name input (already known from Task 4, reviewer nudged it from "not actionable" to "cheap, do it" given it can now co-occur with a logo upload, orphaning the file on the resulting 400); (9) `adminBranding.test.ts` doesn't test the field-isolation convention the whole UI depends on (PATCH one field, confirm others survive untouched) or logo replacement (the untested branch that hides Important #1).

Also flagged: `discussion-custom-branding.md` still opens with "Status: decided ... Skip. Not building." with no forward pointer to spec 28, despite spec 28 explicitly saying that file should stay as historical record (correct) — needs a one-line "superseded by" banner, not a rewrite. Separately, spec 28's citation of `docs/decisions.md`'s "Decided, Not Building" section for the original decline is wrong — that section/entry doesn't exist there; the real text is in `gap-analysis.md` (itself now stale for other already-shipped features too, a pre-existing project-wide pattern this branch didn't introduce).

Ruling: scoping the one allowed fix wave to Important #1 (cache-bust `logoUrl` via `?v=<updatedAt-timestamp>`, relax the existing test's exact-match assertion, add a genuine logo-replacement test) plus Minors #2, #3, #4, #7, #8 (all cheap — one-line-to-small-function scale — and either correctness/data-integrity relevant or directly adjacent to code the fix wave is already touching), the field-isolation half of #9 (the specific test the whole UI's Reset-button behavior depends on, currently completely untested), and #10's two doc fixes (trivial, no code risk). Deferring #5 (unsaved-edits-reverted UX trap — a real but non-critical UX polish issue, not this feature's core promise) and #6 (upload allowlist too permissive for logos — real but Admin-gated and explicitly assessed by the reviewer as low severity/"mostly a data-quality issue"), and the remaining #9 test gaps beyond field-isolation (401-no-token, rejected-file-type-on-this-route, appName>100-char — good ideas, lower priority than the two already included). Cost if wrong: the deferred items remain as documented, low-severity debt — none are security-critical on their own, and #5/#6 are both UX/data-quality nuances a real deployment would surface quickly if they mattered in practice.
