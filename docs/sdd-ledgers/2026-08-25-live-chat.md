## Final whole-branch review (opus)

Verdict: Ready to merge — With fixes. 1 Critical, 7 Important, 10 Minor.

Critical: (1) frontend Socket.IO client is a module-level singleton never disconnected on logout — a second user in the same browser tab inherits the first user's authenticated socket identity (stale-user cross-exposure: prior agent's room memberships/broadcasts continue flowing into a tab now used by a different logged-in user; or a newly logged-in agent silently inherits a stale customer identity and live chat breaks permanently for that tab).

Important: (2) JWT verified only at handshake, never re-verified — a socket outlives token expiry/deactivation/role change for as long as the tab stays open; (3) reconnection reuses the stale captured token and Socket.IO does not auto-retry after a middleware auth rejection, so a reconnect after ~15min goes permanently inert with no user-visible error; (4) `claim` is a non-atomic check-then-update — two agents can both pass the Waiting check and the loser gets silently overwritten, then 403s on send after being told claim succeeded; (5) `join-session` ack failures are silently discarded on both frontend pages (dead `joinedSessionRef`, no `else` branch) — masks #1/#3/#4's failures as "chat looks fine, nothing arrives"; (6) `claim`/`end` never broadcast a queue-update event to the `agents` room, so a claimed session lingers in every other agent's Waiting list, causing routine claim-race 409s; (7) a customer has no way to resume a session after reload — `liveSessionId` is component-state-only and the customer-scoped session-list endpoint doesn't exist, so a reload orphans the session (unrecoverable by anyone but an Admin/Manager) and creates a duplicate on next escalation; (8) spec acceptance criterion 4 (agent-vs-agent socket RBAC) is checked as verified but the cited test only covers customer-vs-customer — code is correct on inspection, but the checked box overstates test coverage.

Minor (10, see full review text for all): re-joinable room after Ended (9), can't start second chat without reload (10), missing .catch on history loads (11), DTO type widening (12), repeated io-cast (13), queue role-label mismatch (14), open CORS origin (15), no customer name/wait-time in queue rows (16), non-idempotent re-end (17), no message max-length (codebase-wide gap, not a regression) (18).

Plan/spec-level notes (not implementation defects): `claim`'s room-join was delegated to a client-initiated `join-session` rather than the spec's literal "claim joins the socket" wording — reviewer assessed this as MORE secure (server re-validates rather than trusting the claim request's own socket) and recommended keeping it, but flagged it as an undisclosed deviation not recorded in this ledger at the time. Customer-side session resumption (issue #7) was never specified by the spec or plan at all — a genuine requirements hole, not an implementer miss.

Ruling: scoping the one allowed fix wave to Critical #1 and Important #2-#8 (all concretely actionable, all either security-relevant or break the feature's core promise of a live, reliable queue) plus the three cheapest, directly-related Minors (#9 re-joinable Ended room, #10 can't restart chat, #11 missing .catch on history loads — all one-line-scale and adjacent to the Important fixes already touching the same files). Deferring Minors #12-18 (type widening, DRY cast helper, cosmetic label, CORS allowlist, queue UX polish, idempotency, message length) — none are security- or correctness-critical, several are pre-existing codebase-wide patterns (not regressions), and the skill's "one fix wave" rule argues for a tightly-scoped, verifiable wave over a sprawling one. Cost if wrong: the deferred Minors remain as documented, ledgered debt — visible and correctable later, not silently lost. The retained-deviation note (client-initiated join-session vs. spec's literal wording) is not being reverted — reviewer explicitly assessed the deviation as a security improvement over the spec's literal text; ledgering the disclosure now closes the process gap without touching working, more-secure code.

**New regression found, not caught by the implementer or disclosed in the fix-wave report:** fix #2's periodic re-auth interval re-verifies only the token captured once at handshake time, never refreshed — but the app's pre-existing `apiClient.ts` 401-interceptor silently refreshes the HTTP-layer access token independently, never touching the socket. Access tokens are 15min TTL; the re-auth interval fires every 5min. Socket.IO does not auto-reconnect after a server-initiated disconnect by design, and no `disconnect` handler existed anywhere in the frontend. Net effect: any live-chat socket left open past ~15-20 minutes of entirely ordinary use would be silently and permanently killed, with no visible error (connect_error never fires for this path — it isn't a failed connection attempt) and no auto-recovery short of a full page reload. This directly undercut the reliability promise the whole fix wave existed to protect, for a very ordinary usage pattern.

Ruling: this finding is load-bearing (breaks live chat's core reliability promise for a mainstream case, not an edge case) but the skill caps this plan at one fix-wave dispatch — no second fix-wave subagent round. Since the reviewer's diagnosis pinpointed the exact mechanism and fix location, I (controller) made the fix directly rather than dispatching another implementer: added a `socket.on("disconnect", (reason) => { if (reason === "io server disconnect") socket?.connect(); })` handler in `frontend/src/lib/socketClient.ts`, so a server-initiated kick triggers an immediate manual reconnect, which re-invokes the already-fixed (#3) auth callback to pull the current (already HTTP-refreshed) token — a still-valid user reconnects seamlessly; a genuinely-expired session falls through to the existing connect_error UI. Verified independently: frontend tsc clean, backend 67/67 unaffected (frontend-only change), frontend production build succeeds. Commit c822767. Cost if wrong: worst case is a brief visible reconnect blip every 5 minutes for legitimately active users, or (if the reconnect loop itself were buggy) a repeated connect/disconnect cycle — bounded and observable in the browser console/network tab, not a silent data-loss or security regression; asymmetric risk strongly favors this small, targeted fix over leaving the known-broken behavior shipped.

Residual, non-load-bearing items intentionally parked as documented debt (not further ledgered individually, already covered by the whole-branch review's own severity calibration): Minor #12-18 from the original whole-branch review (DTO type widening, repeated io-cast, CORS allowlist, queue UX polish (customer name/wait time), non-idempotent re-end, no message max-length — codebase-wide, not a regression), plus the newly-surfaced test-coverage gaps for fix-wave items #6 and #9.
