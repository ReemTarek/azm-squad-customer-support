## Final whole-branch review (opus)

Verdict: Ready to merge — With fixes. 0 Critical, 3 Important, 6 Minor.

Reviewer independently re-verified the entire "zero backend surface, no data leak" premise from scratch (not trusting the task reviews) — confirmed via `git diff --stat -- backend/` returning empty across the whole range, confirmed the client-side sort/slice never operates on an unscoped superset (Manager/Admin never even fetch the tickets endpoint; Customer/Agent's fetch is already server-scoped regardless of query params), confirmed `enabled` gating exactly matches backend role requirements with no gaps, confirmed Rules-of-Hooks compliance directly against the shipped file.

Important: (1) the Agent "My Tickets" urgency sort ranks the ENTIRE assigned list including Resolved/Closed tickets, and a ticket resolved or closed after its due window keeps `slaState: "breached"` permanently (confirmed in `sla.ts` and the Closed-transition's `resolvedAt` set) — so a long-lived agent's top-5 list fills with dead closed tickets wearing red Breached badges while live at-risk work gets pushed off, AND this directly contradicts the SLA-alerts tile right below it (which correctly filters to Open/InProgress only) — the reviewer traced why Task 1's live verification couldn't have caught this: the test dataset had zero late-resolved tickets (0% SLA breach rate), so the failure mode was structurally unreachable during verification. (2) none of the 5 queries have an error-state UI — a fetch failure renders a silently blank/incomplete card (worst case: both report queries failing removes the ENTIRE staff dashboard body including the "View full report" escape hatch), inconsistent with this app's own established `role="alert"` pattern already used on `TicketsListPage`/`ReportsPage`. (3) `AuthContext.tsx`'s `logout()` never calls `queryClient.clear()`, and no user-identity is embedded in any query key in this codebase (a pre-existing, app-wide fact) — so a same-tab account switch on a shared workstation can paint the previous user's ticket list for one render cycle before the background refetch resolves; reviewer explicitly frames this as a pre-existing root cause that this feature newly routes onto the landing page (the one page every fresh login hits), recommending the one-line fix land here rather than being deferred elsewhere.

Minor (6): (4) the Admin AI-usage tile only renders `suggestedReply.usedRatePercent`, dropping `chatbot.confidentRatePercent` that the spec's own Scope section named — an undisclosed deviation from the plan's own code (not present at plan-writing time, introduced during implementation) that AC#4 was then checked against as if fully satisfied; (5) AC#3's "scoped to their own department" evidence is digit-identical to the Admin's org-wide numbers, strongly indicating the test Manager had a null department and hit the unrestricted fallback — the equality-with-/reports check still passed but vacuously, never exercising the actual department-scoping half of the criterion; (6) a null-department Manager's dashboard shows unlabeled org-wide numbers with no indication of what population they cover; (7) i18n gaps (hardcoded "min", untranslated status-enum tile titles) — consistent with pre-existing app-wide pattern, not a regression; (8) `["dashboard-tickets"]` duplicates the existing `["tickets",...]` cache key for the same request — wasteful, not incorrect; (9) unbounded fetch-before-slice-to-5 — explicitly spec-accepted at this app's scale, and the fix for #1 reduces this as a side effect anyway.

Ruling: scoping the one allowed fix wave to Important #1 (filter to Open/InProgress before the urgency sort), #2 (add the established `role="alert"` error pattern to all 5 query-dependent sections), #3 (`queryClient.clear()` in `logout()`), and Minor #4 (add the missing chatbot-confident-rate to the AI tile, matching the spec's own Scope wording) and #6 (a one-line scope caption for a null-department Manager/Admin's tiles, cheap and directly adjacent to #4/#5's area). For #5, re-verifying live with a genuinely department-scoped Manager (not re-coding anything, just better test data) is included in the fix wave's own verification step, with the spec's AC#3 evidence corrected to cite the real result. Deferring #7 (i18n gaps, pre-existing app-wide pattern, not a regression), #8 (cache-key dedup, pure performance polish with no correctness impact), and #9 (unbounded fetch, already spec-accepted and already mitigated as a side effect of #1).
