## Final whole-branch review (opus)

Verdict: Ready to merge — With fixes. 0 Critical, 2 Important, 5 Minor, 2 spec/plan-level notes (no undisclosed deviations found beyond the two already ledgered).

Important: (1) `suggested_articles_shown` (`tickets.ts:523-537`) is written even when zero articles were actually shown — including the case where `suggestRelevantArticleIds` short-circuits to `[]` before ever calling Gemini (zero published KB articles), meaning a row is written claiming a call happened when it didn't. This inverts the feature's own Global Constraint ("a 'shown' event must not claim something was shown when it wasn't") and systematically understates `clickRatePercent`, one of the four headline metrics. (2) `POST /ai-usage/event` (`reports.ts:159-165`) validates `ticketId` only as a UUID *shape*, never checks it exists or that the caller can access it — a well-formed nonexistent UUID hits an unhandled Prisma FK violation (500 `INTERNAL_ERROR` instead of 400/404). More significantly: nothing ties a `_used`/`_clicked` client event to a prior real `_shown` event or rate-limits it, so any authenticated staff account can inflate the trust-rate numbers arbitrarily (e.g. loop-posting `suggest_reply_used`) — the exact numbers this whole feature exists to report. Reviewer noted this is staff-only on an internal CRM (not public-facing), but flagged it as a real integrity gap that gets worse the moment a per-agent/per-department breakdown is added (already named as a likely next step in the spec's own Out-of-scope section).

Minor (5, deferred — see full review text for all): a `clickRatePercent` that isn't a well-defined ratio when multiple articles are clicked from one suggestion batch (can exceed 100%); `wasAiSuggestedReply` false-positives beyond the already-known navigation case (select-all-replace, quick-reply-insert over a suggestion); a stringly-typed `countOf` helper duplicated in both the route and its "independent" test cross-check (not independent on that axis); the AI Usage section silently vanishing on a report-endpoint error with no message (matches an existing page pattern, but that pattern already has an error branch elsewhere on the same page); a cosmetic "0% used" render when `shown === 0` but `used > 0`.

Spec/plan-level notes (not implementation defects): the dashboard's Scope names exactly 4 Gemini call sites, correctly matching what got instrumented — `suggestTicketCategory` (feature 26, shipped same day) is legitimately out of this spec's scope, not a missed site, but worth recording as a known gap since a Manager reading "AI Usage" would reasonably expect it to cover all AI usage. Separately, the reviewer flagged that the already-known, out-of-scope `wasAiSuggestedReply`/`replyBody` cross-ticket staleness (TicketDetailPage not remounting on ticket-id param change) has a more serious non-analytics twin: ticket A's AI-drafted reply text can survive navigation and get sent to ticket B's customer — a content-correctness bug, not just a mis-attributed event. Recommended as a separate follow-up (a one-line `key={id}` fix), explicitly not scoped into this feature's fix wave.

Ruling: scoping the one allowed fix wave to Important #1 (one-line guard: `if (suggested.length > 0)` before the write) and the minimal, bounded part of Important #2 — a ticket-existence check (404 via the same `Errors.notFound` pattern already used elsewhere in this codebase, checked before `prisma.aiUsageEvent.create`) that closes both the unhandled-500 bug and the arbitrary-ticket-attribution gap. NOT scoping in the reviewer's optional broader anti-inflation design (requiring a matching prior `_shown` row per user/ticket, and/or rate-limiting) — that's a genuine behavior change with its own design and testing surface, not a bug fix, and the reviewer's own risk assessment (authenticated-staff-only, internal CRM, no public exposure, no displayed number is wrong *today* since there's no per-agent breakdown yet) supports treating it as a documented, ledgered risk to revisit if/when a per-agent breakdown is ever built — which is exactly the trigger condition the reviewer named. Deferring all 5 Minors and the `suggestTicketCategory` scope note as documented debt — none are security- or correctness-critical on their own, several are UX/labeling nuances better handled with real usage data informing the fix. The pre-existing cross-ticket `replyBody` leak (spec/plan note) is explicitly NOT this feature's bug to fix — ledgering it here as a flagged follow-up is the right scope discipline, not a dropped finding. Cost if wrong: the deferred anti-inflation gap remains a real but bounded risk (internal staff-only, no currently-displayed number is corrupted); the deferred Minors remain as documented, easily-correctable debt.
